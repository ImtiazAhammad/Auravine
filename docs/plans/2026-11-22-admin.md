# Admin Site (Phase 5) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (Native, inline). Steps use checkbox (`- [ ]`) syntax.

**Goal:** A protected `/admin` where the owner logs in, edits projects, blog posts, FAQs, tech items and site settings in English and Bangla, uploads images, reads contact messages, and every save shows on the public site immediately.

**Architecture:** The browser only talks to Next.js. Login is a Next.js route handler that exchanges email and password with Supabase Auth and keeps the tokens in httpOnly `SameSite=Strict` cookies. Admin pages are server components guarded by a session check; admin data calls go through `/api/admin/[...path]`, a proxy that adds the access token and forwards to FastAPI `/admin/*`. FastAPI verifies the token with Supabase Auth (`GET /auth/v1/user`), checks the user has a row in `admin_profiles`, then reads and writes with the service-role key and calls `/api/revalidate` after each write. Images upload directly from the browser to Supabase Storage through signed upload URLs issued by FastAPI.

**Tech Stack:** FastAPI, pydantic, httpx2, Supabase Auth (GoTrue REST), PostgREST, Supabase Storage, Next.js 16 route handlers and server components, React 19, `react-markdown` + `remark-gfm` (new), vitest, pytest.

**Spec:** `docs/BACKEND-PLAN.md` (Architecture rules 2 to 4; Phase 5), `docs/plans/phase4-findings.md`, `docs/plans/phase2-findings.md`. Owner-delegated decisions: blog bodies are Markdown (raw HTML off); login is email and password for the existing `admin_profiles` user; v1 screens are projects, blog, FAQs, tech items, site settings, media, messages.

## Global Constraints

- **Only users with a row in `admin_profiles` may use `/admin/*`** (checked on every request in FastAPI, and again by the Next.js layout through `/admin/me`). A signed-up user who is not an admin gets 403 everywhere.
- **Tokens live only in httpOnly, `Secure` (in production), `SameSite=Strict`, `path=/` cookies** (`av_access`, `av_refresh`). They never reach client JavaScript, logs, URLs or response bodies.
- **State-changing admin requests need a same-origin `Origin` header** (checked in the proxy and the login/logout handlers).
- **Service-role key stays in Python.** The Next.js app uses only the anon key, and only for the Auth login/refresh calls.
- **Admin content must not break the public site:** slugs match `^[a-z0-9]+(-[a-z0-9]+)*$`; bilingual `en` is required and non-blank (`bn` optional); link and image URLs are `https://` URLs, site-relative paths starting with `/`, or empty; `details` is validated to the shapes `cleanDetails` accepts; Markdown renders with raw HTML disabled.
- **No deletion of Storage objects in v1** (irreversible). Deleting a content row needs a confirm dialog in the UI.
- **Writes revalidate the site** (`REVALIDATE_URL` with `Authorization: Bearer REVALIDATE_SECRET`). A failed revalidate never fails the save; the response reports `revalidated: false` and the UI says the change may take up to 5 minutes.
- Admin pages are `noindex` and carry no site chrome (no navbar, footer, preloader, chat widget).
- New migrations only add. Every new object gets explicit grants.
- Secrets never appear in git, logs or chat. Real login cannot be verified by the assistant (no admin credentials); everything else is covered by tests and mocks.

## Review Focus

1. **Non-admin or expired/forged token:** every `/admin/*` route returns 401 or 403 and never touches the database. (Task 1, Task 2)
2. **Cross-site request forgery:** a state-changing proxy call without a same-origin `Origin` is refused. (Task 4)
3. **Token leakage:** cookies are httpOnly and strict; login responses and errors never include a token. (Task 4)
4. **Bad admin input cannot break public pages:** invalid slug, blank English, `javascript:` URL, wrong `details` shape are all rejected with a clear error. (Task 2)
5. **Save then view:** a saved change shows on the public page right after the revalidate call; a revalidate failure is reported, not hidden. (Task 2, Task 8)
